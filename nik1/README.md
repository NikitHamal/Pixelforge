# Nik1 — a family of sub-million-parameter, on-device models

Three task-specialised models that run **in a browser tab or on a phone** with no
GPU, no framework and no network. Together they are **437 KB on disk** and answer
in **single-digit milliseconds**. They are deliberately *system-1*: one reflex,
one small model per job, no chain of thought, no context window to manage.

```
nik1-route      utterance -> tool call     248k params · 262 KB ·  28 ms warm
nik1-search     brief -> asset              132k params · 169 KB · 9.2 ms warm
nik1-palette    sprite -> palette family     5k params · 6.6 KB · 0.3 ms warm
```

Everything here is reproducible from this repository: the training data is
*generated from the asset registry*, training runs on a laptop CPU in minutes,
and the exported `.nik1` container is read by a ~700-line dependency-free
JavaScript runtime that runs in Node and the browser from the same code path.

```bash
node nik1/js/bench.js                  # the numbers above, on your machine
node nik1/tools/nik1-gate.js           # full gate: gradients, overfit, parity, budgets
node nik1/tools/nik1-gate.js --fast    # ~30 s profile used by node scripts/verify.js
node nik1/js/demo.html                 # open via scripts/serve.js
```

## What is measured, and what is not

**Measured on this checkout** (2 vCPU container, Node 24, no GPU):

| | nik1-route | nik1-search | nik1-palette |
|---|---|---|---|
| parameters | 248,192 | 132,288 | 5,032 |
| int8 file | 262.0 KB | 142.1 KB + 26.5 KB doc table | 6.6 KB |
| resident weights | 1.58 MB (fp32) / 262 KB (packed) | 738 KB | 20 KB |
| cold load | 12.3 ms | 4.1 ms | 1.2 ms |
| warm latency | 28–36 ms / call | 9.2 ms / query | 0.3 ms / sprite |
| task quality | **88.3% exact call**, 100% tool, 100% schema-valid | **any@1 81.0%**, any@5 91.9% (random 0.9%) | **100%** vs 12.5% majority |
| int8 vs fp32 | identical on every metric | identical | identical |

**Not claimed:** I could not verify the trending tiny-model release you mentioned
(this agent has no web capability enabled), so the "400× cheaper / 200× faster"
framing is *not* repeated here as fact. What is measurable is stated above:
zero marginal cost per call, 437 KB on disk, no network round trip, and
sub-40 ms for the largest model on two CPU cores. Compared with a hosted
frontier call (network + per-token price + a 300 ms–2 s round trip), a local
specialist is 10–100× faster for this narrow task class and costs nothing per
call — that comparison is a methodology, not a benchmark I ran.

## The three specialists

### `nik1-route` — utterance → tool call

```js
const model = await Nik1.loadModel('nik1-route', { baseUrl: 'nik1/js/models/' });
model.setTools(tools, catalog);                       // schemas + asset catalogue
model.routeUtterance('give me the knight', Nik1Grammar, tools, catalog);
// { call: { tool: 'load_template', args: { id: 'rpg_knight' } },
//   source: 'model', notes: [], raw: '{"tool":"load_template",...}', ... }
```

**Reliability is architectural, not statistical.** The model proposes; three
layers dispose:

1. **Token mask** — `{"tool":"` is forced token by token, and inside the name only
   continuations that are a prefix of a *real* tool name are allowed. A
   hallucinated tool is impossible, not unlikely.
2. **Repair** — the output is parsed leniently, coerced against the live schema
   (types, enums, ranges, truncation), and **references are validated against the
   catalogue**: `rpg_deathk` becomes `rpg_deathknight` because that id exists.
3. **Validate + fallback** — the same rules `PF.Tools.validate` applies in the
   studio. If anything still fails, a deterministic keyword router answers.

The pipeline therefore returns a schema-valid call **100% of the time** (300
held-out utterances, int8 weights). What varies with model quality is how often
the model produced it unaided — 98.7% — and how often the call is *exactly* the
one the dataset wanted: 88.3%.

### `nik1-search` — brief → asset

A 132k-parameter bi-encoder trained with InfoNCE over the whole catalogue, then
exported with a **precomputed document table**: the catalogue is static, so a
query costs one short encode plus 106 dot products. Trained and evaluated with a
split *by asset*, so a held-out template contributes no vocabulary to training.

`any@1` counts a hit if the top result shares a tag or category with the request —
the honest metric for "find me something like this", because a one-tag query like
"animal" is legitimately answered by a dozen assets. Exact-id recall is reported
too (1.9%) and is low *by construction*: 91 training templates share tags.

### `nik1-palette` — sprite → colour budget

5k parameters over 41 hand-computable features (luma/saturation/hue histograms,
distinct-colour count, mean/std). Trained on 16,872 balanced rows generated by
rendering every asset in the library through each of eight palette families, so
the classes are balanced by construction and the majority baseline is 12.5%.

The question it answers is the one an artist has when importing unknown art:
*what colour budget is this sprite drawn for?* It is also a demonstration that a
5 KB file can be 100% accurate on a real, non-trivial visual task.

## Using it

### Browser / worker / Node (the runtime)

```html
<script src="nik1/js/nik1.js"></script>
<script src="nik1/js/grammar.js"></script>
<script>
  const model = await Nik1.loadModel('nik1-route', { baseUrl: 'nik1/js/models/' });
  const tools = await (await fetch('nik1/js/models/tools.json')).json();
  const catalog = Nik1Grammar.loadCatalog(await (await fetch('nik1/js/models/templates.json')).json());
  model.setTools(tools, catalog);
  console.log(model.routeUtterance('export a gif at 4x', Nik1Grammar, tools, catalog).call);
</script>
```

There is a self-contained demo at `nik1/js/demo.html` (serve the repo with
`node scripts/serve.js`): router, semantic search, and a draw-your-own sprite
palette classifier, each showing its own latency.

### Shipping the weights: whole or sharded

`loadModel('nik1-route')` reads `nik1-route.nik1` if it is there, and otherwise
joins `nik1-route.nik1.part-NN` using `nik1-route.nik1.parts.json`. Callers never
see the difference — the same call works in the browser, in a worker, and in
Node, and the manifest's sha256 is checked before the bytes are parsed, so a
truncated download fails loudly instead of quietly computing the wrong answer.

Sharding exists because some publishing pipelines cap a single request body at
128 KB, and a model you cannot publish is not shipped. It is not a format
change: a joined file is byte-identical to an unsharded one.

```bash
node nik1/tools/split-model.js split nik1/js/models/nik1-route.nik1 --max 90000
node nik1/tools/split-model.js verify nik1/js/models   # parts present, sizes, sha256
node nik1/tools/split-model.js join  nik1/js/models/nik1-route.nik1
```

The Python reference reads both forms too (`nik1.quantize.model_bytes`), and
`nik1/tools/nik1-gate.js` fails if any shard is missing, over 100 KB, or does not
reassemble to the manifest's byte count and hash.

### Inside the PixelForge studio

`js/agent/nik1-tools.js` registers four tools — `nik1_status`, `nik1_route`,
`nik1_search`, `nik1_palette` — with the same registry the agent console, MCP
manifest and `window.PixelForge.call` already read. They load lazily on first
use, so a page that never needs them never pays for them.

### From the shell

```bash
node nik1/tools/export-data.js --frames 3000      # regenerate the datasets
python3 nik1/python/train_router.py               # 4 min on 2 vCPU
```

## Training on a free GPU (Kaggle)

The NumPy trainer is enough for the shipped sizes. To go bigger, the same
architecture exists in PyTorch and exports to the identical container:

| notebook | what it does | time on a T4 |
|---|---|---|
| [`kaggle/nik1_train_on_kaggle.ipynb`](kaggle/nik1_train_on_kaggle.ipynb) | trains a 2–6M parameter router from scratch | ~15 min |
| [`kaggle/nik1_distill_on_kaggle.ipynb`](kaggle/nik1_distill_on_kaggle.ipynb) | distils an oracle or a real LLM into a ~3 MB student | ~6 min |

```bash
python3 nik1/python/torch/train_router_torch.py --d-model 256 --layers 6 --steps 6000
python3 nik1/python/torch/distill.py --teacher oracle --n 20000
python3 nik1/python/torch/distill.py --teacher hf --model Qwen/Qwen2.5-0.5B-Instruct
```

The runtime does not care which size you load: the architecture travels in the
`.json` beside the weights, and the JS reader builds whatever shape it finds.

## Tests (what "done" means here)

```bash
node nik1/tools/nik1-gate.js
```

| step | what it proves |
|---|---|
| `tests/test_grad.py` | every hand-written backward pass matches central finite differences (7/7) |
| `tests/test_overfit.py` | the stack can memorise 4 examples — catches misaligned targets, dead losses |
| `tests/test_runtime.js` | JS ↔ NumPy parity on token ids, logits, embeddings, labels; tokenizer totality (emoji, CJK); grammar invariants; latency budget |
| `tests/test_js_parity.py` | the Python and JS grammar/repair layers agree case-for-case; containers are aligned, finite, loadable |
| budgets | file sizes, warm latency, metric floors, every shipped container parses |

The overfit test exists because of a real bug found during development: an
off-by-one in the next-token shift made the loss look perfect while the model
learned to copy its own input. Cross-language parity caught another: a missing
final RMSNorm in the encoder's pooling path, and a swapped dimension in the FFN
output projection, both invisible to a single-language test.

## Limitations, honestly

- **`nik1-route` is an in-domain router.** It knows the 52 tool names and the
  argument shapes in this repository, and 88% of held-out *template-generated*
  utterances become the exactly intended call. Free-form phrasing the generator
  never produced will be repaired or fall back rather than answered perfectly.
  The LLM-teacher distillation path exists precisely to widen that coverage.
- **`nik1-search` ranks; it does not reason.** No filters, no dates, no boolean
  logic — those belong in the deterministic layer beside it.
- **`nik1-palette` recognises eight palette families**, not arbitrary palettes.
  Add a family to `nik1/data/palettes.json`, regenerate, retrain: 30 seconds.
- **`any@1` is not precision.** On ambiguous queries the top hit is often an
  equally valid asset; the metric accepts that, and says so.
- **The runtime unpacks int8 to float32 at load** (437 KB → ~2.3 MB resident).
  `keepQuantized` dequantizes inside the matmul instead for the smallest
  footprints; the shipped default favours speed.
